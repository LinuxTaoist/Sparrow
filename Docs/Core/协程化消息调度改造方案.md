# Sparrow 单进程多组件协程化改造方案（最小侵入）

## 1. 背景与问题

当前 SparrowSrv 进程内多个组件共用同一消息事件调度线程。消息处理链路为：

- 主循环进入统一 EpollLoop
- MQ 事件回调中直接收包并同步分发
- 业务 ProcessMsg 在回调路径内直接执行

该模型的直接结果是：任一组件消息处理耗时增加，会阻塞其他组件消息处理，形成组件间相互 delay。

## 2. 设计目标

- 改动小：尽量不改业务模块接口与消息协议。
- 低耦合：业务层不直接依赖具体协程库。
- 易移植：协程运行时可插拔，支持无协程回退。
- 低风险：先保持同模块串行语义，降低行为回归概率。
- 可观测：新增排队与执行维度指标，便于定位瓶颈。

## 3. 约束与不改项

本次架构改造明确不改以下内容：

- 不修改 SprMsg 协议格式与消息 ID 体系。
- 不修改 Mediator 对外语义。
- 不强制修改业务模块 ProcessMsg 函数签名。
- 不要求业务模块直接 include 协程头文件。

## 4. 现状关键路径（用于对照改造点）

- Core/SprObserverWithMQueue.cpp
  - EpollEvent: 收包后直接 DispatchSprMsg
  - DispatchSprMsg: 默认分支直接调用 ProcessMsg
- Core/SprEpollSchedule.cpp
  - 协程开关与注释存在，但未形成真实协程调度
- Components/Basics/SparrowSrv/main_sparrow.cpp
  - 单主循环驱动
- Components/Basics/SparrowSrv/SprSystem.cpp
  - 系统初始化与插件加载入口

## 5. 总体方案（分层）

### 5.1 分层原则

新增“调度抽象层”，把“在哪里执行”与“执行什么业务”分离：

- 业务层：仍保留 ProcessMsg 语义
- 框架层：负责入队、调度、超时、背压、取消
- 运行时层：可插拔协程后端或同步后端

### 5.2 新增核心层次

1) MsgDispatchExecutor（统一执行器接口）
- 职责：Post 任务、按策略调度、统一超时和错误上报。
- 约束：接口不暴露第三方协程类型。

2) ModuleMailbox（模块邮箱）
- 职责：按模块维度排队。
- 默认：每模块 FIFO 串行，保证原有同模块顺序语义。
- 可选：模块并发度可配置（默认 1）。

3) RuntimeAdapter（运行时适配）
- 职责：屏蔽协程库实现差异。
- 后端实现：
  - InlineRuntime（同步兜底）
  - LibgoRuntime（协程后端）

4) BlockingBridge（阻塞桥接）
- 职责：阻塞 I/O 或 CPU 重任务转线程池执行，再回协程继续。
- 目的：避免“协程壳 + 阻塞调用”导致调度线程仍卡死。

## 6. 关键适配点

### 6.1 SprObserverWithMQueue 适配

目标：将“回调内执行业务”改为“回调内快速入队”。

- EpollEvent
  - 保留收包与基础校验
  - 将 Dispatch 任务投递到 MsgDispatchExecutor
  - 立即返回 epoll，缩短回调占用

- DispatchSprMsg
  - 拆分为框架消息快速处理与业务消息任务化处理
  - 保持框架控制消息优先（注册响应、日志等级变更等）

### 6.2 SprEpollSchedule 适配

目标：把现有协程参数变为真实能力，并通过 RuntimeAdapter 注入。

- 统一由配置决定后端（inline/libgo）
- HandleEpollEvent 仅负责事件分发，不承载业务重处理
- 保持无协程配置时行为可回退

### 6.3 SparrowSrv 初始化路径适配

目标：在系统初始化阶段完成执行器与运行时注入。

- main_sparrow 或 SprSystem 初始化时创建 Executor
- 生命周期与主进程一致
- 退出流程支持 drain + cancel

### 6.4 业务模块适配策略

优先“零签名变更”：

- 第一阶段不改 ProcessMsg 签名
- 通过框架调度改造先实现组件隔离
- 慢路径再逐步引入 await 风格接口（增量演进）

## 7. 调度与并发策略

### 7.1 顺序与并发

- 默认策略：每模块串行（并发度 1）
- 扩展策略：热点模块可设并发度 N
- 顺序规则：同 key 保序，跨 key 可并发（可选）

### 7.2 背压策略

- 每模块队列设置 high-watermark
- 超阈值触发：告警 + 限流/降级/丢弃策略（三选一按配置）
- 记录丢弃计数和原因

### 7.3 超时与取消

- 每条消息任务携带 deadline
- 超时后上报并可中断后续步骤
- 系统退出时支持全局取消和队列清理

## 8. 可移植性与解耦设计

- 业务层仅依赖 Core 抽象接口，不依赖 libgo。
- 运行时与业务隔离在 RuntimeAdapter。
- 平台差异控制在适配层，不扩散到 Components。
- 可在不支持协程的平台使用 InlineRuntime 运行。

## 9. 渐进式实施计划

### Phase 1：调度抽象落地（低风险）

- 新增 Executor + Mailbox + InlineRuntime
- SprObserverWithMQueue 改为入队执行
- 业务无感，主要验证行为一致性

交付标准：
- 功能回归通过
- 无明显吞吐回退
- 同模块顺序行为与改造前一致

### Phase 2：协程后端接入（可灰度）

- 新增 LibgoRuntime
- 配置开关按进程或按模块灰度启用
- 选 1 到 2 个慢模块试点

交付标准：
- 组件间阻塞显著下降
- 平均排队时延与 P99 时延下降

### Phase 3：慢路径协程化治理（收益放大）

- 梳理阻塞点并通过 BlockingBridge 分流
- 增加超时、取消、背压闭环
- 扩展到更多业务模块

交付标准：
- 关键链路 P99 达标
- 监控项完整并可定位瓶颈

## 10. 风险与应对

1) 线程安全风险
- 风险：模块并发度提升后暴露共享状态问题。
- 应对：默认并发度 1，按模块白名单放量。

2) 行为语义漂移
- 风险：调度异步化改变时序。
- 应对：保持框架控制消息优先与同模块 FIFO。

3) 伪协程风险
- 风险：阻塞调用未治理导致收益不明显。
- 应对：建立阻塞点清单，逐条桥接到线程池。

4) 可运维性不足
- 风险：问题发生后难定位。
- 应对：增加排队时延、执行时延、队列深度、丢弃计数。

## 11. 配置建议

建议新增统一配置项：

- scheduler.enable_coroutine: true/false
- scheduler.runtime: inline/libgo
- scheduler.default_module_parallelism: 1
- scheduler.module_parallelism.<module_name>: N
- scheduler.queue_capacity.<module_name>: M
- scheduler.task_timeout_ms.default: T

## 12. 验收指标（建议）

- 组件间影响指标：A 组件慢处理时，B 组件消息延迟不显著抬升
- 时延指标：
  - queue_delay_p50/p99
  - execute_time_p50/p99
  - end_to_end_p50/p99
- 稳定性指标：
  - 队列溢出次数
  - 超时任务数
  - 取消任务数

## 13. 阻塞/死锁排查方案（兼容现有 InfraWatch）

你提到的现有能力是正确且应保留的：当前可通过 MQ 状态里的 MIDLAST（最后处理消息 ID）辅助定位问题。

- 现有入口：Debug/InfraWatch/MediatorWatch.cpp
- 现有字段：MIDLAST（lastMsgID）来自 Core/SprMQueueDetails

### 13.1 现有方案的价值与局限

价值：

- 当队列不动或系统卡住时，可快速看到“最近一次处理过哪个消息 ID”。

局限：

- MIDLAST 是“最后完成/记录”的消息，不一定是“当前正在卡住”的消息。
- 协程并发后，同一模块可能有多个 in-flight 任务，单个 MIDLAST 信息不足。

### 13.2 新增观测字段（建议最小集）

在不破坏现有展示的前提下，给每个模块增加运行态快照（可落到共享内存结构，沿用现有读取路径）：

- curMsgID: 当前正在执行的消息 ID（若无执行中则为 0）
- curSigName: 当前消息名称（可选，便于现场直接看）
- curBeginMonoMs: 当前消息开始执行时间（单调时钟）
- curExecMs: 当前消息已执行时长（动态计算）
- curCoId: 当前协程 ID（无协程模式可置 0）
- curState: RUNNING/WAIT_IO/WAIT_LOCK/WAIT_TIMER（枚举）
- queueDepth: 当前模块邮箱深度
- queueDelayMsMax: 队列中任务最大等待时长

### 13.3 更新时机（避免误判）

建议在调度器统一埋点，减少业务侵入：

1. 任务出队、即将执行前：写入 curMsgID/curBeginMonoMs/curState=RUNNING
2. 任务进入等待点（I/O、锁、定时器）时：更新 curState
3. 任务执行完成后：清空 curMsgID，更新 MIDLAST 与统计计数

这样能同时得到：

- 最近处理到哪里（MIDLAST）
- 现在卡在哪里（curMsgID + curState + curExecMs）

### 13.4 InfraWatch 展示建议

在现有 MQ 表格基础上新增列，不破坏老字段：

- MIDCUR（当前执行消息 ID）
- MSTATE（当前状态）
- MEXECMS（当前执行时长）
- QDEPTH（当前队列深度）

保留 MIDLAST，形成“当前 + 最近”双视角。

### 13.5 死锁判定建议（工程规则）

定义两级判定，降低误报：

- 一级告警：curExecMs > warnThreshold（如 2000ms）
- 二级疑似死锁：curExecMs > deadlockThreshold（如 30000ms）且 queueDepth 持续增长

当触发二级疑似死锁时，自动上报：

- 模块名、curMsgID、curState、curCoId
- 持锁信息（若可获取）、等待对象（fd/lock id/timer id）
- 最近 N 条消息轨迹（环形缓冲）

### 13.6 与协程化改造的关系

- 这套机制应作为 Phase 1 同步上线，先于大规模并发放量。
- 无协程与协程模式共用同一套观测结构，避免两套运维口径。
- 业务模块无需感知，仅由框架调度层更新上下文。

## 14. 建议的首批试点范围

- 先选消息量高、处理耗时波动大的业务组件
- 保持核心系统组件（定时、基础管理）先不提并发度
- 每次仅扩一个业务域，确保回滚简单

## 15. 回滚策略

- 一键切回 InlineRuntime
- 模块并发度全部归 1
- 关闭协程开关后仍沿用新调度抽象（避免反复大改）

---

该方案核心价值是：在不动消息协议与业务主接口的前提下，先解决组件间互相阻塞，再逐步把慢路径协程化，最终获得低耦合、可移植、可灰度的演进能力。

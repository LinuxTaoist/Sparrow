# 系统架构

## 1. 架构目标

Sparrow 的整体目标是：在 Linux / 嵌入式设备环境中，提供一套稳定、模块化、可观测的基础运行框架，支持应用层按功能边界扩展。

## 2. 分层视角

从工程结构来看，项目可理解为以下分层：

### 2.1 基础框架层：Core

`Core/` 负责公共能力的封装，包括通用框架基础、事件处理、线程 / 任务管理、消息与信号相关能力等。它应尽量保持通用和稳定，不直接承载具体业务逻辑。

### 2.2 业务组件层：Components

`Components/` 用于放置具体业务服务组件，例如设备服务、任务模块、协议处理模块和应用级功能。这层是扩展业务逻辑的主要入口。

### 2.3 对外接口层：PublicAPIs

`PublicAPIs/` 对外暴露统一能力接口，供上层业务或其他模块调用。这样可以让调用方式稳定，避免业务层直接耦合到内部实现细节。

### 2.4 内部能力层：PrivateAPIs

`PrivateAPIs/` 管理内部协议、内部事件、通信能力和内部依赖关系，主要服务于模块之间的协作。

### 2.5 配置与调试层：Configs / Debug

- `Configs/`：配置项、参数文件、运行配置
- `Debug/`：调试能力、日志入口、状态展示、诊断工具

两者共同支撑系统运行时的观测性和排障效率。

### 2.6 平台适配层：Hardware / Platform

`Hardware/` 和 `Platform/` 用于处理硬件差异、平台差异和环境差异，从而让上层代码尽可能保持通用和稳定。

## 3. 典型调用关系

典型应用方式如下：

1. `Components/` 中新增功能模块
2. 对外能力通过 `PublicAPIs/` 暴露
3. 模块之间通过 `Binder`、消息队列或事件机制通信
4. 运行状态由 `Debug/` 和 `Configs/` 管理
5. `Hardware/` 与 `Platform/` 对接设备及平台差异

## 4. 架构特点

- 模块职责分明
- 业务逻辑和核心框架分离
- 适合长期增量扩展
- 更适合设备端高稳定性系统
- 可观测性较强，便于问题定位和维护

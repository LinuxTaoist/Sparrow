# 工程约束

## 1. 适用范围

本文档用于约束 Sparrow 项目中各模块的公共开发行为，确保工程在跨平台、跨模块、跨版本协作时保持一致性、可维护性和稳定性。

适用范围包括：
- 组件设计与模块边界
- 第三方依赖接入
- 平台适配与接口抽象
- 模块初始化与生命周期
- 线程、内存与资源管理
- 模块间通信与耦合控制

## 2. 通用开发原则

### 编码风格与规范
参考 [C++ 编程规范](C++编程规范.md)。

### 设计原则
- 模块职责应清晰，避免功能堆叠。
- 模块之间尽量减少直接依赖，减少跨模块耦合。
- 业务逻辑与公共基础能力分离，便于后续替换和扩展。
- 优先采用统一接口和统一协议，避免各模块自定义私有规则。

## 3. 第三方依赖与平台适配

### 3.1 第三方库管理
- 第三方库源码统一放在 `Sparrow/3rdParty` 目录下，提供源码压缩包、头文件和静态库文件。
- 公共模块使用第三方库时，不允许直接调用第三方接口，必须通过适配层封装后再提供给模块调用。
- 封装代码统一放在 `Sparrow/3rdAdapter`，第三方头文件仅允许在该目录中体现。
- 这样做的目的，是降低工程与第三方库代码耦合，并方便后续替换或升级依赖。
- 在正式编译前，需先独立交叉编译第三方库，确保版本和环境一致。

### 3.2 平台适配约束
- 硬件控制接口由应用层统一定义，平台实现由各平台继承完成。
- 代码统一放在 `Sparrow/HardWare` 或对应平台目录中。
- 接口设计必须清晰，包括：
  - 业务语义清晰
  - 参数定义清晰
  - 返回值定义清晰
  - 调用方式清晰
  - 调用顺序清晰
- 这样可以确保不同平台的实现行为一致，避免上层业务被平台差异污染。

## 4. 模块初始化与生命周期

### 4.1 启动与停止时序
- 业务模块的初始化逻辑尽量不要放在构造函数中，应放在 `StartWork()` 中，并在收到开机通知后触发。
- 模块的业务销毁逻辑放在 `StopWork()` 中，并在收到关机或待机通知后触发。
- 工具模块可在构造中完成简单初始化，以减少额外调用成本，提升使用方便性。

### 4.2 初始化优先级
- 开机时，有些模块依赖其他模块完成初始化后才能继续工作，因此初始化需要按优先级控制。
- 关机时，也需要按依赖关系等待其他模块完成清理或退出通知。
- 启动依赖其他模块时，应保证依赖模块优先启动，避免出现“依赖未就绪”的运行时错误。

### 4.3 启动超时与重试
- 若模块在开机后 5s 内（时间可配置）未收到开机通知，需要自行触发初始化流程。
- 模块应支持安全退出和重新启动，确保组件可重入。

### 4.4 全局对象与初始化顺序
- 全局对象的初始化顺序不受控制，因此各模块不应依赖其他全局对象的初始化顺序。
- 组件初始化应尽量使用显式启动流程，而不是隐式依赖全局状态。

## 5. 线程管理

### 5.1 线程退出约束
- 若必须使用线程，且线程存在 `loop`（循环函数），必须可正常退出，避免死循环导致资源无法回收。
- 线程退出后必须回收，尽量使用 `join()`，避免使用 `detach()`。
- `detach()` 可能导致线程生命周期不可控，退出状态难以追踪。

## 6. 内存与资源管理

### 6.1 智能指针优先
- 尽量使用智能指针管理资源，如 `std::shared_ptr`、`std::unique_ptr`。
- 优先使用 `make_shared()`、`make_unique()` 分配对象，避免手动调用 `new`。

### 6.2 手动申请的资源
- 若必须使用 `new`，则必须在合适位置使用 `delete` 释放资源，并在释放后置空指针。
- 资源释放必须遵循“创建与销毁成对出现”的原则。

### 6.3 避免内存泄露
- 对动态分配资源需要统一检查释放路径，避免局部或错误分支漏清理。
- 对共享资源、缓存、事件、信号量等，也应按生命周期进行主动释放。

## 7. 模块独立性与通信方式

### 7.1 模块边界
- 每个模块应保持相对独立，减少模块间依赖。
- 尽量减少跨模块调用、跨模块数据传递和共享状态暴露。
- 模块职责应尽量单一，便于测试、维护和替换。

### 7.2 消息通信优先
- 模块间优先通过消息进行通信，而不是直接调用对方内部接口。
- 消息设计应尽量可重入，并尽量减少消息参数数量。
- 过多参数会增加耦合和维护成本，也不利于后续扩展。

### 7.3 选择低耦合方案
- 当存在多种问题解决方式时，应优先选择低耦合、统一处理的方案。
- 例如：组件间启动依赖问题，应尽量在服务拉起处统一解决，而不是在各组件中反复等待和重试。

## 8. 维护建议

- 本文档适合作为工程约束的核心索引，后续新增约束时应沿着同一结构补充。
- 若某项规则与业务需求冲突，需在设计阶段评估并统一约定，而不是在各模块中零散修正。
- 对于关键约束，建议在代码评审和模块设计评审中同步跟进。

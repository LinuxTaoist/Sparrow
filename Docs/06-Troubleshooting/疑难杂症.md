# 疑难杂症

## 1. 组件依赖与初始化顺序

### 问题描述
组件之间的依赖关系复杂，A 依赖 B 的初始化完成状态时，如果 B 启动慢、失败或未完全就绪，A 会提前访问 B 的服务，导致运行时异常或初始化失败。

### 解决方案
1. 从启动策略规避：按依赖图控制启动顺序
   - 建立组件依赖关系图，明确哪些组件必须先启动。
   - 在启动脚本中增加依赖检查，只有前置依赖完成初始化后，后续组件才允许启动。
   - 具体参考 `ServiceManager::StartAllExesFromConfigure`。
2. 从组件内部规避：异步初始化 + 事件通知
   - 对初始化耗时长的组件，采用异步初始化方式，并在完成后通过消息通知依赖组件。
   - 依赖组件收到前置依赖完成事件后，再执行自己的初始化。
3. 从监控日志定位
   - 为关键初始化步骤记录状态和耗时，便于快速定位卡住点。

## 2. 触发安全退出机制后，部分进程出现 crash

### 问题描述
终端输入 `killall -10 servicemanagersrv` 触发组件安全退出机制后，发现 `/dev/shm/` 路径下仍残留大量文件。进一步排查后发现，部分进程在退出时发生 crash，导致资源未能正常回收。

```shell
$ killall -10 servicemanagersrv
$ ls /dev/shm/
sem.OneNetMqtt_req33372  sem.OneNetMqtt_rsp33372  sem.property_service_req79933
sem.OneNetMqtt_req40994  sem.OneNetMqtt_rsp40994  sem.property_service_rsp79933
```

### 解决方案
1. 分析
   - 在触发组件安全退出机制时，发现部分进程在退出时出现 crash，导致未正常回收资源。
   - 在程序行结束，各模块对象进入析构时，出现静态单例对象析构调用另一个静态单例对象（已销毁），导致程序 crash。
2. 两种解决方案
   1) 增加静态原子变量标记对象是否已销毁。

      ```c++
      static std::atomic<bool> gObjAlive(true);

      PropertyManager::~PropertyManager()
      {
         gObjAlive = false;
      }

      PropertyManager* PropertyManager::GetInstance()
      {
         if (!gObjAlive) {
            return nullptr;
         }

         static PropertyManager instance;
         return &instance;
      }
      ```

      - 单例析构中，置静态全局变量 `gObjAlive` 为 `false`。当程序退出时，会调用析构，`gObjAlive` 为 `false`。此时其他组件再次调用 `PropertyManager::GetInstance()`，只要检查是否为 `nullptr` 即可。
      - 关键点是：程序退出时，静态全局变量 `gObjAlive` 也会被销毁，但因为它没有析构函数，值不会被改写，因此可用作“对象是否已销毁”的标记。

      可通过如下例子验证静态变量销毁后效果：

      ```c++
      #include <iostream>
      #include <atomic>

      // 静态全局变量

      class PropertyManager {
      public:
         static PropertyManager* GetInstance();
         ~PropertyManager();

      private:
         PropertyManager();
         static std::atomic<bool> gObjAlive;
      };

      std::atomic<bool> PropertyManager::gObjAlive(true);

      PropertyManager::PropertyManager() {
         std::cout << "gObjAlive: " << gObjAlive << std::endl;
      }

      PropertyManager::~PropertyManager() {
         gObjAlive = false;
         std::cout << "property deconstruct" << std::endl;
      }

      PropertyManager* PropertyManager::GetInstance() {
         if (!gObjAlive) {
            return nullptr;
         }

         static PropertyManager instance;
         return &instance;
      }

      // 另一个静态全局对象，用于模拟在程序退出时访问已释放的静态全局变量
      class AnotherGlobalObject {
      public:
         AnotherGlobalObject() {
            std::cout << "AnotherGlobalObject constructed" << std::endl;
         }

         ~AnotherGlobalObject() {
            // 模拟在程序退出时访问 gObjAlive
            auto p = PropertyManager::GetInstance();
            printf("p = %p\n", p);
         }
      };

      static AnotherGlobalObject anotherGlobalObject;

      int main() {
         auto manager = PropertyManager::GetInstance();
         if (manager) {
            std::cout << "PropertyManager instance obtained" << std::endl;
         } else {
            std::cout << "Failed to obtain PropertyManager instance" << std::endl;
         }

         // 程序结束时，静态变量自动清理
         return 0;
      }
      ```

      验证效果程序不崩溃，说明方案有效。

   2) 避免单例对象调用析构：

      ```c++
      SprLog* SprLog::GetInstance()
      {
         // never delete this instance
         static SprLog *instance = new (std::nothrow) SprLog();
         return instance;
      }
      ```

      此种方式，单例是 `new` 出来的，不会调用析构，因此单例一直有效。此种方式更简洁，但不能自动回收持有的资源，因此不适合需要资源回收的场景。

## 3. 代码复用与项目定制化

### 问题描述
同一套代码需要在多个项目中复用，同时又要满足各项目不同的功能和产品需求。

### 解决方案
- 模块化设计：将代码拆分为通用模块和定制模块，利用接口、抽象类等统一约定，再在不同项目中实现具体适配或扩展。
- 配置驱动开发：通过配置文件或参数化设计，让同一套代码在不同场景下按配置切换行为（参考配置 `ProjectConfigs/Vendor`）。

## 4. 分支管理与迭代开发

### 问题描述
项目开发中面临多线程任务开发，包括维护稳定版本、新增功能开发及新项目启动，需避免并行开发引起的版本冲突。

### 解决方案
- 版本控制策略：使用适当的分支策略，如主分支用于稳定版本维护，开发分支用于新功能开发，每个功能或修复任务都从主分支拉取新分支，开发完成后再合并回主分支。
- 持续集成与部署：实施持续集成与持续部署（CI/CD），确保代码集成频繁且自动化测试通过，减少集成时的冲突和延迟。

## 5. 项目配置数据遗失

### 问题描述
项目配置数据（如数据库连接字符串、第三方 API 密钥、环境变量等）意外丢失或被错误地覆盖，导致系统无法正常运行，服务中断或功能失效。

### 解决方案
- 安全存储与备份：使用安全的配置管理工具和策略，确保配置数据安全存储、备份和恢复能力。
- 版本控制配置：将配置数据也纳入版本控制系统管理，确保配置的变更可追溯和回滚。

## 6. 测试覆盖率及验收不充分

### 问题描述
系统复杂性增加，自动化测试案例匮乏，覆盖率低，不能过早的及时暴露潜在问题。

### 解决方案
- 全面的测试策略：制定全面的测试计划，包括单元测试、集成测试、系统测试和性能测试等，确保不同层面的测试覆盖。
- 自动化测试工具：使用自动化测试工具和框架，提高测试覆盖率和持续集成效率。
- 建立完善的自动化测试流程：明确每个案例输入输出，实现自动化比对机制（如断言），验证实际输出与预期输出的一致性，记录测试报告。

## 7. 动态阈值管理机制

### 问题描述
系统设计初期通常会为动态容量数据设置阈值上限，以防止数据量突增导致资源耗尽或系统崩溃。但随着业务增长，实际数据量可能逐渐接近甚至超过初始阈值，从而影响正常运行。

### 解决方案
- 动态阈值调整：在设计时内置动态调整机制，根据实际数据增长趋势和系统负载，自动调整存储与处理能力的阈值，并同步触发预警。

## 8. 公共数据类型变更导致的兼容问题

### 问题描述
公共头文件、共用枚举或结构体发生变更后，部分模块没有同步更新、重编译或重启，导致不同组件间对同一数据定义不一致，最终出现消息解析异常、通信失败或运行行为异常。

### 解决方案
1. 统一管理共用数据类型：将跨组件共用的枚举、结构体和宏集中放在公共头文件中，确保所有模块使用同一份定义（参考 `CommonMacros.h`、`CommonTypeDefs.h`、`CoreTypeDefs.h`）。
2. 引入版本号：每次修改公共数据类型时同步更新版本号，并在组件启动时校验版本一致性，便于快速定位“哪个模块未对齐”。（参考宏 `COMMON_MACROS_VERSION`、`COMMON_TYPE_DEFS_VERSION`、`CORE_TYPE_DEFS_VERSION`）
3. 保持兼容性：修改枚举时尽量只新增值，不改已有值；这样旧组件在兼容期内更容易继续工作。

## 9. 异地测试与开发协同

### 问题描述
异地测试与开发协同过程中，沟通延迟和现场信息不足，容易导致问题反馈不及时，定位和复现效率下降。

### 解决方案
- 远程调试与监控：通过实时监控和远程调试，减少跨地域排障延迟（参考 `Debug/RShellX`）。
- 一键日志导出：提供在线和离线两种日志导出方式，方便现场测试人员快速收集证据。

## 10. 编译报错

### 10.1 编译报错：undefined reference to symbol 'sem_close@@GLIBC_2.2.5'

#### 问题描述
编译时报错 `undefined reference to symbol 'sem_close@@GLIBC_2.2.5'`。

#### 解决方案
- `sem_*` 相关接口位于 `pthread` 库中，检查编译脚本是否正确链接了 pthread。
- 若库之间存在链接依赖，在 `CMake` 中使用 `target_link_libraries` 时，应将被依赖的库放在后面。

### 10.2 交叉编译 bin 文件在 arm 上运行报错：/bin/sh: ./servicemanagersrv: not found

#### 问题描述
交叉编译生成的 bin 文件，arm 执行时报错 “/bin/sh: ./servicemanagersrv: not found”。

#### 解决方案
- 通过 `file servicemanagersrv` 命令查看文件类型，对比正常可执行的 bin 文件。

```shell
$ file servicemanagersrv
servicemanagersrv: ELF 32-bit LSB shared object, ARM, EABI5 version 1 (SYSV), dynamically linked, interpreter /lib/ld-linux.so.3, for GNU/Linux 3.2.0, BuildID[sha1]=86aab950869c071d3834ac5ed1d2a4d7dc055fa8, with debug_info, not stripped

$ file test
test: ELF 32-bit LSB shared object, ARM, EABI5 version 1 (SYSV), dynamically linked, interpreter /lib/ld-linux-armhf.so.3, for GNU/Linux 3.2.0, BuildID[sha1]=cc78a66419f729997043cb1b236ada4a8c5bfa0b, stripped
```

- 对比发现，两者 interpreter 有差异。在 CMake 中将 `servicemanagersrv` 的 interpreter 修改为 `/lib/ld-linux-armhf.so.3`。

```shell
set(CMAKE_EXE_LINKER_FLAGS "-Wl,-dynamic-linker,/lib/ld-linux-armhf.so.3")
```

- 重新编译运行，问题解决。

# 编码习惯

> 目标：命名准确、逻辑清晰、行为可验证、修改风险可控。规则保持简洁，便于日常查阅和维护。

## 1. 命名
- 名称应简洁、准确地表达实际含义，避免无助于理解的冗余前缀和难以理解的缩写；用于区分类别或保持同组命名一致的前缀可以保留，如枚举项和 Debug 函数。
- 函数名优先使用“动词 + 对象”，如 `LoadConfig()`、`CheckNetwork()`、`ApplyRoute()`。
- 查询函数使用 `Get`、`Query`、`Is`、`Has` 等前缀，名称应体现查询对象；需要修改状态的函数应明确表达其副作用。
- 布尔变量使用 `is`、`has`、`can`、`enable` 等明确前缀。
- 同一概念在不同模块中使用统一名称；错误码、状态值和配置项应直接表达业务含义。

## 2. 函数设计
- 一个函数尽量只负责一项明确职责；复杂流程由入口函数编排，并拆分为有意义的步骤。
- 函数保持适当长度；仅在职责独立、可复用或能明显提升可读性时拆分，不为缩短代码机械增加辅助函数。
- 重复出现的查询、循环和状态处理应合理复用，避免为了复用而强行抽象。
- 查询函数尽量无副作用；修改状态的函数使用明确的动作名称。
- 参数较多时，优先使用结构体或清晰的参数对象。
- 返回值应能表达执行结果，不要只依赖日志判断成功或失败。
- 对有副作用、需要记录或复用结果的调用，先保存返回值再判断；简单的布尔谓词可直接用于条件。

## 3. 类与接口设计
- 类成员按可见性和职责分组，优先将调用方需要的 `public` 接口放前面，实现细节放在 `private`；仅在必要时使用 `protected` 或友元。
- `public` 接口应保持最小，只暴露调用方必需的稳定能力；成员状态不直接暴露给外部修改。
- 新增接口前先评估现有能力和扩展点；只有职责独立、边界清晰时才新增接口，避免为偶发需求暴露底层细节。
- 平台相关操作下沉到平台接口或 HAL；业务层不重复实现底层查询、格式解析和平台适配。
- 跨层调用时，在边界处转换错误码、数据结构和状态语义。
- 保持已有公共 API 稳定；修改接口前检查所有调用方和实现方。
- 类较大时按职责拆分，不要只靠成员排列掩盖职责过多。
- 成员函数按返回类型和职责分组，同类接口尽量相邻；成员变量按类型和职责分组，简单类型通常放在复杂对象之前。
- 构造函数、析构函数和特殊成员函数应易于查找；构造函数初始化顺序应与成员声明顺序一致。

## 4. 错误处理与日志
- 检查所有可能失败的操作；无法处理的错误应向上传递或转换为明确的业务错误码，不要静默吞掉。
- 在模块边界转换系统错误码、HAL 错误码和业务错误码，避免混用。
- 明确处理无效参数、空指针、空字符串和边界值；失败路径尽早返回，减少不必要的嵌套。
- 可以容忍错误时，也应记录错误状态；错误日志应包含操作、对象和失败原因等关键信息。
- 区分“操作成功”和“结果正确”；设置或修复后应按需重新查询验证。
- 日志应说明发生了什么、处理对象及结果；错误日志标明失败阶段，避免笼统的 `failed`。
- 同一错误只在最有定位价值的层级记录一次；正常路径减少无价值日志。
- 日志级别、格式和措辞遵循所在模块的习惯；变量值应符合实际语义。
- 格式化输出中的类型必须与格式符匹配，特别注意 `size_t`、指针和 64 位整数。

## 5. 流程与状态
- 初始化、启动、停止和销毁等流程应保持对称，状态变化应有明确入口。
- `Start()`、`Stop()`、`Repair()` 等入口负责流程编排，具体动作由职责清晰的步骤完成。
- 修复流程应在操作后复查状态，不能仅以“已尝试”表示恢复成功。
- 多阶段处理通常按“查询 → 校验 → 执行 → 验证”组织。
- 连续诊断遇到关键失败时及时返回，避免继续执行无意义的步骤。
- 状态查询失败时，不要继续使用可能过期的状态，除非设计明确允许。
- 异步操作应区分“已提交”“处理中”和“已完成”等阶段。

## 6. 资源与生命周期
- 优先使用 RAII 管理文件、锁、映射、线程、队列和动态内存，并明确资源的创建者、使用者和释放者。
- 裸指针只用于非拥有型引用；拥有关系优先使用智能指针或明确的资源封装。
- 管理动态资源的类应明确拷贝、移动和析构语义，避免重复释放。
- 释放资源后不得继续访问相关对象、句柄、迭代器或映射地址。
- 不依赖静态对象析构顺序管理跨模块资源；析构函数应简单可靠，避免复杂的全局清理逻辑。
- 构造函数和析构函数中不调用虚函数；基类析构函数不依赖子类状态。需要通过基类指针销毁对象时，基类析构函数应为虚函数。
- 构造函数和析构函数中尽量不创建或回收线程；线程生命周期由明确的 `Start()`、`Stop()` 等接口管理。

## 7. 并发与异步
- 修改共享状态前明确同步方式，锁的保护范围应尽量小。
- 不要仅因“当前没有持锁者”就判断共享资源可以销毁。
- 明确线程、队列、epoll 和定时器等对象的创建、使用、停止和销毁顺序。
- 共享资源的初始化和销毁应考虑多线程、多进程并发；打开已有队列或共享资源时，不要默认清空内容，除非调用方明确要求。
- 异步初始化完成前，不要假设服务或连接已经可用；消息处理应区分成功返回 `0` 与失败返回负值。
- 退出流程中不得继续使用已关闭的文件描述符、队列或共享内存。

## 8. 容器与迭代器
- `erase()` 后对应迭代器立即失效，不得继续访问。
- 遍历期间修改容器时，使用容器支持的安全方式；删除元素前先保存后续需要的信息。
- 访问容器前明确处理空容器、越界和查找失败。
- 不必要时避免复制大型对象或容器，优先使用 `const` 引用。

## 9. 协议与数据解析
- 字节流解析必须支持半包、粘包和跨次读取；遇到坏帧时应尝试重新同步，避免丢弃后续合法帧。
- 长度、偏移、计数和边界必须在访问数据前校验。
- 协议字段的单位、字节序和有效范围应在代码或接口处明确。
- 外部数据解析失败时保留足够上下文；部分解析成功时明确标记错误，避免被误认为完整成功。

## 10. 语言与依赖
- 以项目启用的 C++ 标准为准，优先使用标准库能力；线程和互斥锁优先使用 `std::thread`、`std::mutex` 等标准组件。
- 根据访问方式和生命周期选择合适的 STL 容器。
- 引入第三方库前，先确认标准库或项目现有能力无法满足需求，并评估依赖规模和维护成本。
- 尽量减少第三方依赖；非必要时不使用 Boost，时间相关功能优先评估系统接口或项目已有封装，减少对 Chrony 库的依赖。

## 11. 代码组织与风格
- 优先保证逻辑清晰，不追求过度压缩或炫技写法。
- 注释解释“为什么这样做”，不重复描述代码；复杂的时序、所有权、线程安全和协议约束应留下简短说明。
- 复杂条件拆成有意义的局部变量或辅助函数；协议常量、超时、容量和标志位应命名，避免魔法数字。
- 代码修改遵循最小变更原则；新增实现前先参考所在模块的命名、日志和错误处理习惯。
- 仅在逻辑属于类职责时将辅助函数设为该类的 `private` 成员；通用且仅当前翻译单元使用的底层辅助逻辑可保持文件内可见。
- 成员函数仅在不依赖实例状态且适合作为类级能力时使用 `static`；局部变量默认不加 `const`，仅在表达真实不变量或有实际防误改价值时使用。
- 控制单行长度；多行参数和表达式按逻辑分组换行。
- 缩进使用 4 个空格，按实际嵌套层级对齐，不混用 Tab 和空格。
- 代码应兼容项目的 C++ 标准，并在开启警告和 `-Werror` 时保持无警告。
- 文件末尾保留换行。

## 12. 修改与验证
- 修改前确认调用链、资源生命周期和错误传播路径。
- 修改函数签名、错误码或公共结构体时，同步检查所有调用方。
- 修复问题时优先补充可复现的测试或验证步骤，并覆盖成功、边界、超时、重复调用和异常退出等相关场景。
- 构建通过不等于功能正确；并发、进程间通信和生命周期改动还应进行运行验证。
- 测试失败时区分代码问题、测试环境问题和已有基础设施问题。
- 未经验证，不要宣称问题已修复或功能已支持。

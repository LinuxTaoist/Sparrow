# 编码习惯

> 目标：命名简洁准确、逻辑易读、行为可验证、修改风险可控。条目保持短小，便于后续补充。

## 1. 命名

- 函数名优先使用“动词 + 对象”，如 `LoadConfig()`、`CheckNetwork()`、`ApplyRoute()`。
- 查询函数使用 `Get`、`Query`、`Is`、`Has` 等前缀，名称应体现是否修改状态。
- 布尔变量使用 `is`、`has`、`can`、`enable` 等明确前缀，避免含义模糊的名称。
- 命名尽量简洁准确，避免无意义的重复前缀和过度缩写。
- 同一概念在不同模块中使用统一名称，避免同物多名。
- 错误码、状态值和配置项名称应直接表达业务含义。
- 名称应描述实际行为，避免使用与真实语义不符的名称。

## 2. 函数设计

- 一个函数尽量只负责一个明确职责。
- 公共入口函数负责流程编排，具体查询、校验和动作拆成独立函数。
- 重复出现的查询、循环和状态处理应封装复用。
- 函数返回值应表达执行结果，不要只依赖日志判断成功或失败。
- 查询函数尽量无副作用；修改状态的函数使用明确的动作名称。
- 参数较多时，优先考虑结构体或明确的参数对象。
- 不为了复用而强行抽象，抽象应减少重复并提升可读性。
- 保持函数短小，复杂逻辑拆分为有意义的步骤。

## 3. 类定义与成员布局

- 类成员按可见性和职责分组，通常将 `public` 接口放在前面，`protected`、`private` 实现细节放在后面。
- 简单类型成员尽量放在前面，复杂对象、容器和资源句柄放在后面。
- 相同类型或相同职责的成员尽量放在一起，减少来回查找。
- 成员变量、构造函数、公共接口和辅助函数保持稳定、清晰的排列顺序。
- 成员函数返回值尽量保持一致；同一组接口优先使用统一的成功、失败和状态表达方式。
- 同类函数尽量连续排列，例如初始化、启动、停止、查询和修复函数分别成组。
- 构造函数、析构函数和特殊成员函数放在类接口的显眼位置。
- 基类构造函数和析构函数中尽量不调用虚函数，避免访问尚未构造或已经析构的子类部分。
- 构造函数和析构函数中尽量不创建、回收线程，线程生命周期应由明确的 `Start()`、`Stop()` 等接口管理。
- 基类析构函数不应依赖子类状态或执行复杂的异步清理，避免生命周期时序导致随机崩溃。
- 确需通过基类指针销毁对象时，基类析构函数应声明为虚函数；这不等同于在析构过程中调用虚函数。
- 头文件中优先展示调用者需要了解的接口，具体实现和内部辅助成员放在后面。
- 类较大时按功能拆分，避免仅依靠成员排列来隐藏过多职责。

## 4. 错误处理

- 每个可能失败的操作都应检查返回值。
- 不要吞掉错误；无法处理时应向上传递或转换为明确的业务错误码。
- 系统错误码、HAL 错误码和业务错误码应在边界处转换，避免混用。
- 错误日志应包含操作、对象、参数和错误原因等关键信息。
- 日志内容保持简洁，避免重复打印同一错误。
- 失败路径应尽早返回，减少多层嵌套。
- “执行成功”与“结果正确”分开判断；设置、修复等操作完成后应重新验证。
- 对无效参数、空指针、空字符串和边界值进行明确处理。
- 可以容忍错误时，也应记录错误状态，不要静默忽略。

## 5. 状态与流程

- 初始化、启动、停止和销毁等生命周期应保持对称。
- `Start()`、`Stop()`、`Repair()` 等入口只做流程编排，具体动作拆分复用。
- 修复操作不能只表示“已尝试修复”，必须以复查结果确认是否恢复。
- 多阶段流程通常按“查询 → 校验 → 执行动作 → 再查询验证”组织。
- 连续诊断遇到首个关键失败时及时返回，避免执行无意义的后续步骤。
- 状态查询失败时，不要继续使用可能过期的旧状态，除非这是明确设计。
- 异步操作应明确区分“已提交”“处理中”和“已完成”。

## 6. 资源与生命周期

- 优先使用 RAII 管理文件、锁、映射、线程、队列和动态内存。
- 明确对象所有权：谁创建、谁使用、谁释放。
- 裸指针只用于不拥有对象的引用；拥有关系优先使用智能指针或资源封装。
- 涉及动态资源的类应明确拷贝、移动和析构语义，避免重复释放。
- 不要依赖静态对象析构顺序管理跨模块资源。
- 释放资源后不要继续访问相关对象、句柄、迭代器或映射地址。
- 共享资源的初始化和销毁必须考虑多进程、多线程并发使用情况。
- 析构函数应尽量简单可靠，避免依赖其他全局对象的复杂逻辑。

## 7. 容器与迭代器

- `erase()` 后对应迭代器立即失效，不再访问该迭代器。
- 删除容器元素前，先保存后续需要使用的字段。
- 遍历期间修改容器时，使用容器支持的安全遍历方式。
- 不必要时不要复制大型容器或对象，优先使用 `const` 引用。
- 访问容器前明确处理空容器、越界和查找失败情况。

## 8. 并发与消息处理

- 修改共享状态前明确保护方式，锁的作用范围应尽量小。
- 不要仅根据“当前没有持锁者”判断共享资源可以销毁。
- 线程、队列、epoll 和定时器等对象的创建、使用和销毁顺序必须明确。
- 消息处理要区分“成功返回 0”和“失败返回负值”，避免把有效结果误判为失败。
- 打开已有队列或共享资源时，不要默认清空其中内容，除非调用方明确要求。
- 异步初始化完成前，不要假设服务或连接已经可用。
- 退出流程中避免继续使用已关闭的文件描述符、队列和共享内存。

## 9. 协议与数据解析

- 字节流解析必须支持半包、粘包和跨次读取。
- 遇到坏帧时应尝试重新同步，避免丢弃后续合法帧。
- 长度、偏移、计数和边界检查应在访问数据前完成。
- 外部数据解析失败时，应保留足够上下文用于定位。
- 协议字段的单位、字节序和有效范围应在代码或接口处明确。
- 部分解析成功时，应明确标记错误状态，避免将结果误认为完整成功。

## 10. 接口与分层

- 平台相关操作下沉到平台接口或 HAL，业务层不直接执行平台命令。
- 类和模块对外暴露的接口应尽量少，只提供调用方真正需要的能力。
- 在满足功能的前提下，类的 `public` 成员应尽量少，优先使用最小访问权限。
- 成员变量不直接暴露给外部操作，应通过明确的成员函数维护状态和约束。
- 实现细节、辅助函数和内部状态应隐藏在 `private` 或合适的内部模块中。
- 减少 `protected` 和友元的使用；只有确有必要共享内部实现时才使用，并限制使用范围。
- 接口应围绕稳定、独立的职责设计，避免为偶发需求暴露底层细节。
- 新增功能时优先评估现有接口和扩展点，能复用或合理扩展时不要重复新增接口。
- 只有职责独立、边界清晰的功能才考虑新增接口，避免接口数量随功能增长而不断膨胀。
- 接口越少，使用方式越简单，后续实现变化对调用方的影响越小。
- 默认实现可以返回“不支持”，但返回值和日志应保持明确。
- 跨层调用时，在边界处完成错误码、数据结构和状态语义转换。
- 业务层不应重复实现底层查询、格式解析和平台适配逻辑。
- 保持已有公共 API 稳定；修改接口前先确认所有调用方和实现方。

## 11. 语言与库的选用

- 优先使用 C++11 原生语法和标准库能力，线程、互斥锁等优先使用 `std::thread`、`std::mutex` 等标准组件。
- 容器优先选用 STL 容器，根据访问和生命周期需求选择 `vector`、`list`、`map`、`set` 等合适类型。
- 编码过程中尽量减少引入第三方库，避免为简单功能增加额外依赖。
- 非必要时不使用 Boost；优先采用 C++11 和 STL 中已有的简洁实现。
- 尽量少使用 Chrony 库；时间相关功能优先评估原生系统接口或项目已有封装。
- 引入第三方库前，应确认标准库或现有代码无法满足需求，并评估接口复杂度、依赖规模和维护成本。
- 不因库功能丰富而引入库，优先选择接口简单、依赖清晰、项目易于维护的实现。

## 12. 可读性与维护

- 代码优先保证逻辑清晰，不追求过度压缩或炫技写法。
- 注释解释“为什么这样做”，不要重复描述代码本身。
- 复杂的时序、所有权、线程安全和协议约束应留下简短注释。
- 复杂条件应拆成有意义的局部变量或辅助函数。
- 避免“魔法数字”；协议常量、超时、容量和标志位应命名。
- 修改时遵循最小变更原则，不顺手重排无关代码。
- 新增实现前先参考同模块已有命名、日志和错误处理习惯。
- 代码应在开启警告和 `-Werror` 的条件下保持无警告。
- 以 C++11 支持范围为准，避免引入项目未启用的语言特性。
- 代码、日志、注释和接口说明的表达应简洁、准确、可检索。

## 13. 日志习惯

- 日志优先描述“发生了什么、处理的对象是什么、结果是什么”。
- 错误日志应说明失败阶段，不要只打印笼统的 `failed`。
- 同一错误只在最有定位价值的层级记录一次，避免层层重复打印。
- 正常路径减少无价值日志，关键状态变化保留必要信息。
- 日志格式和级别应与所在模块保持一致。
- 打印类型必须匹配格式化字符串，特别注意 `size_t`、指针和 64 位整数。
- 日志中的变量值应与实际业务语义一致，避免打印过期状态或未初始化数据。

## 14. 修改与验证

- 修改前先确认调用链、资源生命周期和错误传播路径。
- 修改函数签名、错误码或公共结构体时，必须同步检查所有调用方。
- 修复问题时优先补充能复现问题的测试或验证步骤。
- 验证不仅覆盖成功路径，也覆盖空值、超时、重复调用、异常退出和资源不存在等路径。
- 构建通过不等于功能正确；并发、进程间通信和生命周期问题还应进行运行验证。
- 测试失败时先区分代码问题、测试环境问题和已有基础设施问题。
- 未经验证，不要宣称“已修复”或“已支持”。
